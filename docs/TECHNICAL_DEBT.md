# Technical debt register — Group 11

Technical debt is a past implementation choice that makes future changes or verification more costly. It is not the list of all features the team would like to add. This register follows Lecture 08's principal/interest distinction and includes knowledge debt: hidden assumptions and undocumented reasons can be costly even when the code works.

Priority is relative to this local, single-user course application. Owners below are proposed roles, not claims that a named student completed work. Every repayment must preserve the existing behavior through tests and update evidence.

## Repaid verification shortcut

TD-07 / locally repaid: `/api/state` previously rebuilt TF-IDF for unchanged inputs. `RankedJobsCache` now retains one complete-input-keyed result, prevents mutable aliasing and serializes concurrent identical requests. Fourteen targeted tests cover invalidation, failure retention and concurrency. A 1,200-job synthetic local benchmark measured median uncached 201.321 ms and warm 52.661 ms; cold cache adds hashing/copying overhead. Memory still grows with corpus size and status changes intentionally invalidate the cache. See RANKING_CACHE.md. This is one measured repayment, not a claim all performance debt is gone.

The new quality workflow has measured evidence: unittest-first red/green logs, doctest-first path validation, five killed targeted mutants, and a package verification report. The five mutations are isolated experiments, not changes left in production. These checks lower regression risk for future refactoring; they do not close unrelated UI, cache or reproducibility debt.

## Feature backlog kept separate

Adding more recruitment sources, multilingual model prompts, a hosted multi-user service or a new research visualization would add capabilities. Their absence is not by itself technical debt. A human-labelled relevance benchmark is an outstanding evaluation need, not proof that current ranking code is defective. Treat the absence of such evidence as a limit on accuracy claims.

## Review cadence and decision rule

At the next substantive change, inspect the affected debt items and estimate the concrete change cost. Repay when the present feature crosses the recorded trigger or when repeated fixes show greater interest than a tested refactor. Record what was deferred, the accepted consequence, and the observable completion criterion. A debt item is closed only after its verification evidence exists; proposed work and unperformed peer reviews stay open.
